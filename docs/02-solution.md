# 技术方案

## 运行契约

CLI 以 JSON 文件接收 `question` 和可选的 `history`。用例通过 `--variant`、`--mode` 和 `--fail-tool` 选定资料版本、运行模式和故障条件。默认加载含两条报销制度的 `conflict` 版本。输出包含 `status`、`answer`、`citations`、`gaps`，需要追问时增加 `follow_up_question`。

| 状态 | 含义 |
| --- | --- |
| `answered` | 已读原文足以支持答案。 |
| `needs_clarification` | 缺少确定适用规则所需的信息。 |
| `out_of_scope` | 检索可用，但资料不足以回答。 |
| `tool_error` | 关键工具失败，且现有证据不足以完成任务。 |
| `incomplete` | 触及执行上限或模型无法继续，记录具体原因。 |

## 资料与工具

`data/` 保存合成 FAQ 和制度。文档包含 ID、标题、版本日期和带 ID 的原文片段。数据变体分别覆盖单条规则、冲突规则和替换期限，同一用例的资料版本随记录保存。

| 工具 | 参数 | 返回 |
| --- | --- | --- |
| `search_docs` | 检索词、结果数量 | 候选文档 ID、标题、版本日期、摘要与片段定位。 |
| `read_passage` | 文档 ID、片段 ID | 指定片段的原文和版本信息。 |

检索按匹配的文档关键词、标题和原文词项排序。首轮命中不足时，模型可把口语表达改写为业务词再搜索。历史对话用于解析指代，答案的证据来自本次成功读取的片段。

## 决策循环与引用校验

1. 将问题、可选历史和动作定义交给模型。模型以结构化动作选择 `search_docs`、`read_passage`、`answer`、`ask_clarification` 或 `stop`。
2. 程序校验动作与参数。执行工具后，把实际结果或结构化错误加入上下文，交回模型决定继续检索、读取、回答、追问或停止。
3. 模型在结束动作中提供引用定位。程序只从本轮成功读取的结果中填入原文、文档 ID、版本日期和片段 ID。缺少有效引用或仍有待解决的资料缺口时，程序驳回 `answer` 并把错误交回模型。语义上的证据支持关系由回归断言与人工审读核验。
4. 默认最多 8 个模型决策步、6 次工具调用。在发出下一次调用前检查相应预算。需要继续执行但预算用尽时，返回 `incomplete`，保留已核实的引用并记录触及的上限。

冲突场景中，读到不同期限后补查适用范围、优先级或替代关系。如果查证仍缺少裁决依据，输出两个期限及其原文并追问适用制度。单独的版本日期不足以裁决冲突。只召回 D01 且本轮未发现冲突时，可在 D01 明确支持的范围内回答。

真实模式用模型选择下一步，代码约束可用动作、引用和执行预算。离线 Mock 用受控动作驱动同一条执行链路。真实模式连接失败时会记录 `model_error`，Mock 由独立命令启动。

使用原生 Python 循环和标准库 HTTP 客户端，便于复核每次调用。模型通过兼容 Chat Completions 的接口返回 JSON 动作，默认使用百炼 `qwen3.8-flash`。[百炼接口文档](https://help.aliyun.com/zh/model-studio/compatibility-of-openai-with-dashscope)

Trace 记录运行模式、模型标识、资料版本、步骤、动作、工具参数、工具结果或错误、下一动作及基于观察结果的简短依据。保留的理由只用于复核动作。运行证据见[评估](03-evaluation.md)。
